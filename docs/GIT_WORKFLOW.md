# Git Workflow

## Branch Model
- `main` is the only integration branch.
- All active work goes into topic branches created from `main`.
- Use one branch per change:
  - `feature/<topic>`
  - `fix/<topic>`
  - `refactor/<topic>`
  - `chore/<topic>`

## Daily Flow
```bash
git checkout main
git pull --ff-only
git checkout -b fix/ocr-question-count
```

Do the smallest complete change, then commit only code, tests, and required config.

## Commit Rules
- Keep each commit rollback-safe.
- Do not mix OCR fixes, report styling, worker runtime fixes, and unrelated frontend work in one commit.
- Preferred commit prefixes:
  - `feat: ...`
  - `fix: ...`
  - `refactor: ...`
  - `test: ...`
  - `chore: ...`

Example:

```bash
git commit -m "fix: stabilize OCR top-level question counting"
```

## What Must Stay Out Of Git
- Local environments: `venv/`, `node_modules/`
- Build outputs: `.next/`, `dist/`, `__pycache__/`, `*.tsbuildinfo`
- Runtime data: SQLite databases, uploads, generated reports
- Local-only files: `.env`, `.vscode/`, `.claude/`, debug logs, Codex diagnostics

If a file is generated by running the system, it should normally be ignored.

## Release Rules
- Tag only stable milestones.
- Recommended tags:
  - `v0.1.0`
  - `v0.2.0`
- Use tags for meaningful capability checkpoints, for example:
  - OCR stabilized
  - Celery upload flow stabilized
  - six-dimension scoring redesign completed
  - PDF layout stabilized

## Remote / PR Rules
- Add a remote repository before long-term development continues.
- Do not push directly to `main` once remote collaboration starts.
- Merge through PRs, even for single-person work, when you need a review trail and rollback history.
